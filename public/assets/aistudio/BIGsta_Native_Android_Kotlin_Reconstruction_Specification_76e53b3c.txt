BIGsta — COMPLETE NATIVE ANDROID KOTLIN RECONSTRUCTION

PROJECT OBJECTIVE

Reconstruct BIGsta as a proper native Android application using Kotlin.

This is not a WebView conversion and not simply a website redesign.

The objective is to create a modern Android application with native Android navigation, screens, menus, buttons, dialogs, notifications, background services and SMS integration.

The existing BIGsta web application is the reference for business logic, database communication, user workflows and administrator functionality.

We want to improve the Android experience without breaking the existing backend.

CRITICAL RULE: RECONSTRUCT THE INTERFACE AND ANDROID-SPECIFIC FUNCTIONALITY, NOT THE EXISTING DATABASE CONTRACTS.

PHASE 5 — NATIVE SMS AND TRANSACTION INTEGRATION

We need native Android functionality that the web application cannot reliably provide.

The objective is to support legitimate, user-consented transaction SMS processing.

A. Transaction SMS receiver

Implement an Android-native SMS integration for supported payment and transaction notifications, subject to Android permissions and distribution requirements.

Before enabling this functionality:

1. Explain to the user what messages will be processed.
2. Request the necessary permissions only when legally and technically permitted.
3. Let the user enable or disable transaction SMS monitoring.
4. Allow configuration of supported transaction message senders or formats.
5. Clearly show whether SMS monitoring is active.

Do not read or upload unrelated personal conversations.

Do not collect an entire SMS inbox.

B. Transaction message parsing

For supported transaction confirmation messages, extract only the necessary fields:

- Transaction reference/code.
- Transaction amount.
- Transaction date and time.
- Sender or payment provider.
- Transaction type where identifiable.
- Relevant account identifier where explicitly required by the existing BIGsta backend.

Preserve the exact transaction reference.

Parse amounts carefully, including decimal values and currency formats.

Do not confuse:

- Transaction reference codes.
- Payment confirmation codes.
- Login OTPs.
- Banking authentication codes.

Do not forward login OTPs, passwords, PINs or banking authentication codes to the database.

The transaction reference must be treated separately from authentication secrets.

C. Database forwarding

After validating a supported transaction message:

1. Identify the correct transaction.
2. Extract the approved transaction fields.
3. Validate the amount and transaction reference.
4. Check for duplicates.
5. Associate the record with the correct authenticated BIGsta user.
6. Send the record through the existing approved backend integration.
7. Store the transaction using the existing database structure.
8. Record processing status.
9. Update the transaction interface when the server confirms successful processing.

Do not mark a transaction as approved merely because an SMS was received.

The existing backend must perform the necessary verification and approval.

Implement:

- Duplicate transaction prevention.
- Retry handling.
- Network failure handling.
- Pending upload queue.
- Delivery status.
- Error logging without exposing sensitive message contents.

Use a unique transaction reference or suitable idempotency mechanism to prevent repeated processing.

D. Background processing

Use suitable native Android components.

Use:

- BroadcastReceiver where permitted.
- WorkManager for persistent upload retries.
- Coroutines for asynchronous processing.
- Foreground services only when genuinely necessary and compliant with Android restrictions.

Do not keep an unnecessary permanent background service running.

Do not claim background SMS monitoring works when the required permissions or platform conditions are unavailable.

E. SMS permissions and policy compliance

Android SMS access is restricted.

Use the SMS Retriever API or SMS User Consent API for supported OTP verification workflows.

For financial transaction SMS processing, implement only an eligible, disclosed and user-consented use case.

Do not assume that adding READ_SMS or RECEIVE_SMS automatically makes the functionality eligible for Google Play distribution.

If unrestricted SMS permissions are not permitted for this app's distribution model, provide a compliant alternative such as explicit transaction-message sharing or user-assisted submission.

Do not secretly use notification access or another permission to bypass SMS restrictions.
